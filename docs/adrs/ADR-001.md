# ADR-001: Cluster distribution — k3s vs Talos Linux vs kubeadm

> **Status:** Accepted
> **Date:** 2026-05-24
> **Deciders:** Platform owner

---

## Context

The platform requires a Kubernetes cluster running on a Dell laptop with an Intel Pentium N3710 processor, 4 cores, and 8 GB RAM. The node runs Ubuntu Server. The cluster is single-node. The platform is operated by a single person with no dedicated operations team.

The 8 GB RAM budget is shared between the OS, Kubernetes system pods, the observability stack, and all running applications. This constraint rules out any distribution or approach that carries significant system overhead. It is the primary driver of this decision.

Three approaches were evaluated for bootstrapping and operating the cluster. They are not the same category of tool — k3s is a packaged Kubernetes distribution, Talos Linux is an OS designed around Kubernetes, and kubeadm is a bootstrapping utility for vanilla Kubernetes on an existing OS. They are compared here as alternative answers to the same question: how does the platform run Kubernetes on this hardware?

---

## Options considered

| Option | Summary | Pros | Cons |
|---|---|---|---|
| k3s | A lightweight, single-binary Kubernetes distribution designed for edge and resource-constrained environments, installed on top of an existing OS. | Sub-512 MB memory footprint. Single binary. Installs in minutes on Ubuntu Server. Bundles Traefik, Flannel, and CoreDNS. Active community. Low ongoing operational burden. | Opinionated defaults (bundled CNI, ingress) require explicit configuration to override. Less suitable for large multi-node production clusters — not a concern for this use case. |
| Talos Linux | An immutable, API-driven Linux OS built exclusively for running Kubernetes, where the OS and Kubernetes bootstrap are a single unified system. | Minimal attack surface due to immutable OS. No unnecessary userland tooling. Strong security posture out of the box. | Replaces Ubuntu Server entirely — a destructive change to the existing node. No traditional shell or SSH access; all management is via `talosctl`. Higher operational complexity on a single-node personal platform where those security benefits are not proportionate to the cost. |
| kubeadm | A bootstrapping tool that installs and configures individual Kubernetes components (kubelet, etcd, kube-apiserver) on an existing Linux system. | Full control over every component. Standard upstream Kubernetes with no distribution opinions. | Not a distribution — requires manual lifecycle management of each component independently. Higher memory footprint from running full upstream Kubernetes components. Operationally expensive for a solo operator, disproportionate to the requirements of this platform. |

---

## Decision

The platform uses k3s as the Kubernetes distribution, installed on the existing Ubuntu Server node.

---

## Rationale

k3s was chosen primarily because its memory footprint fits within the 8 GB RAM budget without sacrificing functionality. Its single-binary model reduces operational complexity to a level appropriate for a solo-operated platform, and its bundled components (Traefik, Flannel, CoreDNS) remove the need to provision and manage those dependencies independently at bootstrap.

Talos Linux was rejected because it would require replacing the existing Ubuntu Server installation — a destructive, high-effort change to the base node. Its management model (`talosctl`-only, no SSH, no shell) adds operational complexity that is not justified on a single-node personal platform. The security benefits of an immutable OS are real, but they are disproportionate to the operational cost at this hardware profile and scale.

kubeadm was rejected because it is a bootstrapping tool, not a distribution. Operating a cluster bootstrapped with kubeadm requires the operator to manage each Kubernetes component's lifecycle independently — upgrades, certificates, and configuration changes all require direct intervention. This overhead is inappropriate for a solo operator on constrained hardware where a purpose-built lightweight distribution is available.

---

## Consequences

### What this makes easier

- Cluster bootstrap is a single command on the existing Ubuntu Server node.
- Traefik ingress and Flannel CNI are bundled and require no separate provisioning.
- Cluster upgrades are managed via the k3s upgrade controller, reducing manual intervention.
- The existing Ubuntu Server familiarity is preserved — standard Linux tooling, SSH access, and package management remain available.

### What this makes harder

- Bundled components (Traefik, Flannel) require explicit configuration to override or replace if requirements change in a later phase.
- k3s does not support multi-node high availability without additional tooling. This is not a current requirement, but transitioning to HA in a future phase would require additional planning.
