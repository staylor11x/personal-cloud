# ADR-002: GitOps operator — ArgoCD vs FluxCD

> **Status:** Accepted
> **Date:** 2026-05-24
> **Deciders:** Platform owner

---

## Context

The platform requires a GitOps operator to manage declarative application manifests, ensure continuous reconciliation from a single source of truth (Git), and provide a simple operational model for a solo operator working on a single-node Kubernetes cluster with 8 GB RAM. The operator must run reliably within the constrained memory budget shared by the OS, Kubernetes system components, observability tooling, and applications.

A single operator is expected to perform verification, troubleshooting, and occasional manual reconciliation tasks. A graphical view of the cluster state is valuable for rapid verification when only one operator is available. If no decision is made, ad hoc imperative tooling would increase operational burden and reduce reproducibility.

---

## Options considered

| Option | Summary | Pros | Cons |
|---|---|---|---|
| ArgoCD | A Kubernetes-native GitOps operator that provides a server component and a web UI for application and cluster resource visualisation. | Web UI with resource tree and sync/diff views aids a single operator in verifying desired vs actual state; strong application-level visibility; mature feature set (Helm, Kustomize, sync hooks); active community and documentation. | Higher memory and component footprint compared to FluxCD (server, repo-server, application-controller, optional Dex); slightly greater operational overhead on resource-constrained single-node hardware. |
| FluxCD | A lightweight, Kubernetes-native GitOps operator composed of small controllers focused on reconciliation (source-controller, kustomize-controller, helm-controller, notification-controller). | Lower resource footprint and simpler component model; aligns closely with Kubernetes controller patterns; minimal runtime memory usage when configured conservatively. | No first-class built-in web UI in the core project (visualisation requires extra tooling); visibility and ad-hoc verification workflows are primarily CLI-driven which increases operator effort for manual checks. |

---

## Decision

The platform uses ArgoCD as the GitOps operator for application delivery.

---

## Rationale

ArgoCD was chosen because its web UI and application-focused visualisations materially reduce the effort required by a single operator to verify deployment and diagnose drift. The platform's hardware constraint (single-node, 8 GB RAM) was a primary consideration; the memory overhead of ArgoCD is higher than FluxCD but remains acceptable within the 8 GB budget when optional components are disabled and resource requests are tuned. The operational efficiency gained from immediate visual feedback, sync/diff operations, and a centralized application view outweighs the incremental resource cost for a solo-operated, single-node platform.

FluxCD was rejected not on technical merit but because its CLI-first verification model increases manual operational work for a single operator. FluxCD remains a valid future option if the platform transitions to a multi-node environment where minimizing controller memory usage becomes the dominant constraint.

---

## Consequences

### What this makes easier

- Visual verification of application and cluster state via the ArgoCD web UI.
- Faster diagnosis of drift and easier manual sync operations for a single operator.
- A single source of truth and familiar application-centric view for audits and onboarding.

### What this makes harder

- Slightly higher memory consumption on the single-node 8 GB platform; requires tuning of ArgoCD component resource requests and disabling optional features where appropriate.
- Additional components to manage and monitor (ArgoCD server, repo server, application controller). The operator must add lightweight monitoring alerts for ArgoCD resource pressure.
