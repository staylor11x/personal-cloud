# ADR-002: GitOps tooling — ArgoCD vs FluxCD

> **Status:** Accepted
> **Date:** 2026-05-24
> **Deciders:** Platform owner

---

## Context

The platform manages all cluster state declaratively through Git. A GitOps controller is required to reconcile the desired state in Git with the running state of the k3s cluster. Without a GitOps controller, cluster changes must be applied manually with `kubectl`, which introduces drift, removes auditability, and is incompatible with the GitOps-first design principle established in [docs/architecture.md](../architecture.md).

The platform runs on a single Dell laptop with an Intel Pentium N3710 processor, 4 cores, and 8 GB RAM. It is operated by a single person with no dedicated operations team. The 8 GB RAM budget is shared between the OS, Kubernetes system pods, the observability stack, and all running applications. Any GitOps controller must operate within this constrained resource budget.

Two tools were evaluated as answers to the same question: which GitOps controller reconciles Git-declared state to the k3s cluster with a resource footprint and operational model appropriate for this platform?

---

## Options considered

| Option | Summary | Pros | Cons |
|---|---|---|---|
| ArgoCD | A Kubernetes-native GitOps controller with a built-in web UI, providing declarative application delivery and continuous reconciliation from Git. | Rich web UI for monitoring and verifying application sync state. Widely adopted across the industry with strong community support and documentation. Declarative `Application` and `AppProject` CRDs provide clear, auditable configuration. Rollback and sync history visible without CLI access. | Higher base memory footprint than FluxCD. Requires deploying the ArgoCD server component alongside the controller. |
| FluxCD | A CNCF-graduated GitOps toolkit composed of discrete controllers (source-controller, kustomize-controller, helm-controller) installed as separate Kubernetes resources. | Lower memory footprint due to composable controller architecture — only required controllers are installed. CNCF-graduated project with strong GitOps Toolkit interoperability. | No built-in web UI — deployment state can only be observed via `flux` CLI or external dashboards. Additional tooling required to gain visibility into sync state. Modular design adds configuration surface area for a solo operator. |

---

## Decision

The platform uses ArgoCD as the GitOps controller for continuous reconciliation of cluster state from Git.

---

## Rationale

ArgoCD was chosen because its built-in web UI provides direct, accessible visibility into application sync state, deployment history, and drift detection without requiring CLI access or additional observability configuration. For a solo operator, the ability to verify that a deployment has reconciled correctly from a browser is operationally valuable and reduces the time spent diagnosing synchronisation issues.

FluxCD was rejected primarily because it provides no built-in UI. Gaining equivalent visibility into deployment state would require integrating an external dashboard such as Weave GitOps or constructing custom Grafana panels — additional operational work that is disproportionate to the requirements of a single-operator platform. FluxCD's lower memory footprint is a meaningful advantage, but ArgoCD's resource consumption remains acceptable within the 8 GB RAM budget when deployed on the k3s cluster alongside the committed observability stack.

The 8 GB RAM constraint ruled out any tool that would require significant additional supporting infrastructure to achieve equivalent operational capability. ArgoCD provides that capability natively within a resource profile appropriate for this hardware.

---

## Consequences

### What this makes easier

- Deployment state, sync history, and application health are visible through the ArgoCD web UI without additional tooling.
- Rollbacks can be initiated from the UI or CLI without manual manifest intervention.
- ArgoCD `Application` resources provide a clear, auditable mapping between Git paths and cluster namespaces.
- The GitOps reconciliation loop is observable without SSH access to the node.

### What this makes harder

- ArgoCD's memory footprint is higher than FluxCD. If memory pressure becomes a constraint in a later phase, the ArgoCD deployment will require resource tuning.
- ArgoCD introduces its own RBAC model and `Application` CRD surface area that must be understood and configured before applications can be deployed through it.
- The ArgoCD server component requires ingress and authentication configuration to be usable securely — this must be in place before the UI is exposed, even internally.
