# ADR-008: CI/CD architecture — self-hosted vs hosted runners, bootstrap dependency

> **Status:** Accepted
> **Date:** 2026-05-24
> **Deciders:** Repository owner

---

## Context

The platform requires CI/CD automation across two distinct phases of operation: before the k3s cluster exists, and after it is running. GitHub Actions is the chosen orchestration layer for all CI/CD.

Two categories of job must be supported. The first is PR validation — linting, manifest validation, secret scanning, and automated code review — which must run before any code is merged to main, including during Phase 1 when the cluster does not yet exist. The second is post-merge deployment — triggering ArgoCD to sync updated manifests to the cluster and running smoke tests — which logically requires the cluster to be reachable.

This creates a bootstrap dependency. A self-hosted runner executes as a process on the k3s node and can reach the cluster API directly. However, the runner cannot be provisioned until Phase 1 is complete and the node is running. Using only a self-hosted runner is therefore impossible during Phase 1: the runner does not exist yet. Using only GitHub-hosted runners is also insufficient: they run in ephemeral cloud VMs with no network path to the cluster, so post-merge deployment jobs cannot be executed from them.

A decision is required on how to structure the runner strategy to satisfy both constraints: PR validation that works before the cluster exists, and post-merge deployment that has cluster access once it does.

---

## Options considered

| Option | Summary | Pros | Cons |
|---|---|---|---|
| GitHub-hosted runners only | Use GitHub-hosted runners for all CI/CD jobs, both PR validation and post-merge deployment. | No infrastructure dependency — works from day one, before the cluster exists. Simple, single runner type to maintain. | GitHub-hosted runners have no network access to the cluster. Post-merge deployment and ArgoCD sync cannot be triggered from a GitHub-hosted runner. |
| Self-hosted runner only | Provision a self-hosted runner on the k3s node and use it for all CI/CD jobs from the start. | Single runner type. Runner has direct cluster access for deployment jobs. | The self-hosted runner cannot exist before the k3s node is provisioned. Phase 1 PR validation cannot run — the bootstrap dependency makes this option impossible during the foundation phase. |
| Dual-runner strategy | Use GitHub-hosted runners for PR validation and the self-hosted runner on k3s for post-merge deployment jobs. | PR validation works immediately, before the cluster exists. Post-merge deployment runs on the runner with cluster access. The Phase 1 workflow definition requires no changes when the self-hosted runner is added in Phase 2. | Creates a sequencing dependency: post-merge deployment jobs are unavailable until the self-hosted runner is provisioned in Phase 2. Phase 1 merges do not trigger ArgoCD sync automatically. |

---

## Decision

The platform uses a dual-runner strategy. GitHub-hosted runners execute all PR validation jobs — linting, `kubeval`, Helm lint, Gitleaks secret scanning, Copilot review, and CodeRabbit analysis. The self-hosted runner on the k3s cluster executes all post-merge deployment jobs — ArgoCD sync triggers and smoke tests. This separation maps directly to the CI/CD boundary: GitHub-hosted runners provide CI, the self-hosted runner provides CD.

---

## Rationale

The self-hosted-only option was rejected because it is not viable during Phase 1. The runner process depends on the k3s node existing and being configured, which is the output of Phase 1, not a precondition for it. Requiring the runner to exist before Phase 1 merges can be validated creates a circular dependency.

The GitHub-hosted-only option was rejected because GitHub-hosted runners run in ephemeral cloud VMs managed by GitHub with no inbound or outbound network path to a private home cluster. Post-merge deployment requires the runner to reach the cluster API or ArgoCD endpoint directly. This is structurally impossible from a GitHub-hosted runner without exposing the cluster to the public internet, which the security model explicitly prohibits.

The dual-runner strategy resolves the bootstrap dependency cleanly. PR validation is stateless and requires no cluster access, making it a natural fit for GitHub-hosted runners. Post-merge deployment requires cluster access and is only meaningful once the cluster exists, making it a natural fit for the self-hosted runner. The workflow definition for PR validation does not need to change when the self-hosted runner is added in Phase 2 — the two job types are independently defined and do not share runner configuration.

---

## Consequences

### What this makes easier

- PR validation works from the first commit in Phase 1, before any infrastructure is provisioned, because it runs entirely on GitHub-hosted runners
- The self-hosted runner can be added in Phase 2 without modifying existing PR workflow definitions — the runner type is scoped per job, not per workflow
- Post-merge deployment jobs have direct, private network access to the cluster because they run on a process inside the node
- The CI/CD boundary is explicit and enforced by runner type — a deployment job cannot accidentally run on a GitHub-hosted runner, and a validation job does not depend on the cluster being available

### What this makes harder

- Phase 1 merges to main do not trigger ArgoCD sync automatically. The self-hosted runner is not available until Phase 2, so post-merge deployment is a manual operation during Phase 1
- The self-hosted runner must be provisioned, registered, and maintained as part of Phase 2 cluster setup. If the runner process stops, post-merge deployment jobs fail until it is restarted
- Two runner types must be kept consistent with the workflow job labels. A mismatch between the `runs-on` label in a workflow file and the registered runner name causes silent job queuing failures
